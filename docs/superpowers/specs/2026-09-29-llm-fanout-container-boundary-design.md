# Isolated-container boundary for llm-fanout repository writers

Status: approved 2026-09-29 for implementation under the [container-boundary plan](../plans/2026-09-29-llm-fanout-container-boundary.md). Approval does not enable provider spend or authorize a repository write; the plan's staged gates control those actions. This supplements the [multi-repository design](2026-09-27-llm-fanout-multi-repo-design.md); that document's target, evidence, handover, and external-action gates remain in force.

## Outcome and decision

An untrusted Claude, Codex, or agy CLI must be able to edit only its disposable, target-specific seat workspace and resume its exact session. It must not read the caller's repositories, sibling seats, credentials, memory gateway token, host home, or Docker control socket. The controller alone verifies a candidate and hands it to the already specified local ticket-branch protocol. Read-only v1 execution stays available while this boundary is built; v2 and repository-writing provider launches stay closed until the final live certificate.

The current macOS Seatbelt route cannot meet that contract for all three installed CLIs: Codex needs host IPC outside the proved policy, and agy needs a local listener and has not completed exact cold resume. Do not widen Seatbelt permissions to make a test pass. The selected replacement is one dedicated, mount-audited Linux VM containing one networkless container per seat. A VM per seat would offer a stronger kernel boundary but add a VM lifecycle and image for every round; a shared Docker bridge would be simpler to wire but give seats a network path. Neither is selected for this slice. This choice is an inference from the measured native failures and [Docker's documented `none` network](https://docs.docker.com/engine/network/drivers/none/), not a claim that a container alone is a sufficient security proof.

The CLI process, its prompts, and candidate files are untrusted. The macOS controller, dedicated VM kernel and Docker daemon, guest relay, and host broker are trusted components to minimize and attest. This is not a defense against a compromised VM/daemon, a malicious same-user host process, or an administrator changing the machine underneath a run. The accepted host-side Git handover still checks repository identity and CAS, but this design does not claim safety against adversarial between-syscall replacement of its metadata pathname. That exclusion must be stated in a release claim, not silently converted into a container test gate.

## Trust domains and data flow

```text
macOS controller: plan, journal, candidate verification, memory, credentials
       │ authenticated host–VM tunnel: broker and bounded evidence channels
       ▼
dedicated Linux VM: credential-free relay and Docker daemon; no host mounts
       │ one guest-local, permit-bound Unix socket per seat
       ├── Claude container: private workspace + private session volume
       ├── Codex container: private workspace + private session volume
       └── agy container: private workspace + private session volume
```

The host controller builds each workspace from the captured target baseline and approved staged evidence; the seat never sees the caller checkout or its `.git` directory. Every seat receives the same admitted plan in control context, but filesystem access is limited to its own target and explicitly staged evidence. Peer answers move through the controller's existing blind-first-round barrier, verified claude-mem checkpoints, and target-bound dependency records. Seats do not share a writable volume, memory token, or ambient peer directory. The controller accepts a candidate only through the existing target-bound verification and handover protocol.

The host–VM tunnel has separate typed operations. Its SSH transport uses strict server-host-key checking with an owner-held Ed25519 pin; Colima's generated localhost SSH route does not establish that identity. A private sidecar binds the dedicated profile, Lima instance and disk, Docker context metadata and endpoint, and pinned key before later starts. Host-to-guest import carries a controller-authenticated, target/seat-bound immutable manifest of baseline, staged skills, plan context, and evidence, with canonical relative paths, allowed file kinds/modes, digests, count and byte limits. Guest-to-host export carries bounded candidate and raw transcript artifacts under the same identity. Import and export stage privately, validate every entry and digest, then publish atomically; a guest never supplies a host destination path or arbitrary command. The host controller stores exports in its private artifact store and verifies candidates afresh. The broker channel is distinct from these transfer operations and cannot become a file-transfer or host-exec API. No macOS host filesystem is mounted into the VM.

The VM is a separate profile, not the default or Maka profile. Its effective host mounts must be empty, including implicit mounts, before any seat starts. In Colima, an explicit empty `mounts: []` currently maps to a writable home mount, while a nil mount list means no mounts; configuration text alone is therefore insufficient. Inspect the generated VM configuration, guest mount table, and each container's `docker inspect` mounts at admission and recovery. [Colima source](https://github.com/abiosoft/colima/blob/main/config/config.go#L728-L744) defines this surprising default. Any host home, checkout, socket, or Docker-daemon mount fails closed. The implementation plan must choose and pin the exact VM launcher/profile mechanism, prove that it can maintain a no-host-mount profile, and keep the other profiles untouched.

The controller pins each Linux image by digest and each CLI executable by byte hash and version. A seat runs non-root with a read-only root filesystem, private PID/IPC namespaces, dropped capabilities, no new privileges, explicit CPU/memory/process limits, and only named private workspace/session volumes plus its one guest-local relay socket. It receives no Docker socket, privileged flag, host namespace, or macOS host bind mount. That socket is the only VM-local path bind-mounted into its container; inspect and reject every other bind mount. Docker's security model treats daemon control and host mounts as powerful capabilities, so they are outside the seat boundary. [Docker security](https://docs.docker.com/engine/security/), [bind-mount behavior](https://docs.docker.com/engine/storage/bind-mounts/).

`--network none` leaves container loopback available, which should permit agy's local listener without any route to the VM, host, sibling containers, or internet. Prove that property with actual negative connections; do not infer it from a command flag or an inspect JSON alone. Each seat's Unix socket leads only to a credential-free VM relay. The host-side broker, not the seat or VM relay, obtains provider credentials and applies the existing strict provider/path/model/body/output limits. The VM relay forwards only the controller-issued bounded protocol over one authenticated host–VM tunnel. It must not become an arbitrary HTTP proxy, return a credential, or expose a general host port. The exact tunnel mechanism is a prerequisite no-spend probe: if a long-lived, authenticated stdio or equivalent VM channel cannot be shown without a host mount or seat-visible network route, this design remains blocked. No fallback to an unrestricted bridge or host-loopback TCP route is implicit.

## Admission, recovery, and evidence

Introduce a versioned container-seat descriptor rather than treating a caller-supplied JSON or the old Seatbelt descriptor as authority. The controller must bind run, task, target, seat, inputs digest, admitted provider profile, exact executable/image, VM identity and effective mounts, container runtime settings, workspace and session volume identities, socket/relay identity, broker permit, and initial-or-resume route. At initial launch, Claude may use its caller-issued session ID; Codex and agy begin in an explicit `initial:unassigned` state. On a successfully verified initial terminal, the controller validates the observed CLI session ID and durably binds it to the exact turn and session-volume identity before allowing resume. Every resume requires that recorded ID. At every launch and cold recovery, the controller re-reads live VM/container state and authenticates the descriptor against its durable record. A changed image, mount, volume, network mode, session, profile, or broker permit refuses before model spend. The public `run_provider` path must dispatch only an explicitly certified boundary type; test-injected runners and a green no-spend fixture cannot lift it.

The session volume survives an initial turn and its exact-ID resume, and is private to one seat. A cold controller enumerates labeled containers for that run, quarantines or stops orphan processes, revokes the old relay/permit epoch, and reattests the image and volumes before creating another container. Broker request counts and consumed/uncertain spend are durable controller state, not merely in-memory counters. A send whose outcome is uncertain is never replayed automatically; recovery records an explicit duplicate-spend disposition. Test broker and relay interruption before send, after send, and during response streaming. The controller may not search ambient CLI state or replay completed provider turns. If a CLI cannot demonstrate exact initial and resume behavior on its pinned Linux build, that profile remains disabled; full three-executor repository-write certification and retirement parity remain blocked. Agy's macOS resume hang is not presumed to disappear on Linux. Unknown model IDs, extra provider requests, malformed broker responses, credential reflection, and stale source/profile hashes block without a reconciled result.

No container process writes a caller repository. Its candidate is copied out as bounded evidence, reverified in a fresh workspace, then applied through the separate local Git CAS handover. This amendment does not change branch naming, same-ticket multi-repository ownership, Jira/PR/deploy authorization, or the external-action barrier. The host-side metadata-path race excluded above remains a disclosed limitation of the trusted-host assumption, not an unstated release prerequisite that the container design can satisfy.

## Verification and rollout

1. No-spend VM probe: build a disposable dedicated profile, record the effective mount/network inventory, confirm no host mount, and exercise a fake seat/relay/broker and bounded import/export with one target and a sibling target. The profile remains isolated from default and Maka. A failed mount or transport probe leaves the public write gate closed.
2. Hermetic tests: deny host checkout, `.git`, home, secrets, sibling workspace/session, Docker socket and VM networking; allow only own workspace, loopback, session, and permit-bound socket. Test changed image, VM mount, container mount, network mode, volume, profile, socket, permit, target, and session at initial and cold resume. Exercise bounded HTTP/SSE, import/export path and digest attacks, secret-reflection, timeout, permit-budget, and broker-restart cases.
3. Private live certification: a controller-issued disposable certification harness uses the *same* container launcher, relay, broker policy, and provider adapter as proposed production dispatch, but binds synthetic roots and cannot authorize a caller-repository write or change the public gate. It obtains initial and exact-ID cold-resume evidence for pinned Linux Claude, Codex, and agy builds with no provider credentials inside seat or VM relay. Capture raw transcripts, process/container/VM attestations, model identity, source hashes, negative isolation evidence, and durable broker spend disposition. A missing profile remains disabled; no partial result counts as the required all-three certificate.
4. Trial certificate and two-repository trial: after the private harness passes, review the complete source for both certificate gates. A versioned *trial* certificate can authorize only named synthetic roots and exact disposable targets; the separate public `run_provider` gate already exists but stays closed without a release certificate. Both certificates bind the same final runtime hash, VM/profile and effective mounts, image/CLI digests, relay/broker code and route, permits, and each profile's initial/resume and isolation evidence. Repeat the private live probe on these final source bytes before issuing the trial certificate. Then run the accepted two-repository disposable DAG, peer exchange, candidate verification, local ticket branches, partial failure, and cold recovery through the certified boundary. Use Maka to evaluate quality separately; a Maka score cannot certify isolation.
5. Release certificate and strict gate: only after the synthetic trial succeeds, run current-source read-only canaries, the full deterministic gate, strict skill receipts, and skill installation/doctor on the *same* final source hash used by the trial. Any subsequent source change invalidates those results and requires the private live probe, synthetic trial, and strict checks again. Issue a separate owner-held *release* certificate bound to that checked source hash, the successful trial, and all final gate receipts. Public dispatch requires this release certificate; the trial certificate can never satisfy it. A per-profile diagnostic may be recorded while the all-three release gate remains red; it is not Forge/Council parity.
6. Release posture: keep feature flags and production actions outside this boundary. A public branch must be rebuilt from clean public main with synthetic fixtures and no private tickets, hidden oracles, local run receipts, or inherited private history. No Forge/Council retirement or real caller-repository writing claim precedes the strict gate and an owner-approved real caller-repository trial. A ticketless work session needs a reviewed generic branch identity or an actual assigned work item; an invented ticket key is not admission.

The first implementation plan should be split at the measured VM transport/mount proof. A failed proof ends the plan with a documented blocker; it must not relax the isolation contract. All lab resources need exact names, recorded ownership, and an explicit teardown review before removal. This design alone makes no VM/configuration change.
